# War Gaming

لعبة حرب جماعية بالفرق للهاتف، ثنائية الأبعاد — تدعم **اللعب أونلاين** مع
الأصدقاء عبر الإنترنت، و**اللعب المحلي عبر البلوتوث** بدون إنترنت. فريقان
(أحمر/أزرق)، حركة بعصا تحكم افتراضية، إطلاق نار، ونقاط حياة — يفوز الفريق
الذي يقضي على الفريق الآخر بالكامل.

## بنية المشروع

```
war-gaming/
├── server/    خادم Node.js (WebSocket) — المرجع الرسمي للعب الأونلاين
├── mobile/    تطبيق Flutter + Flame — الواجهة ومحرك اللعبة (android/ios جاهزان)
└── docs/      شرح تقني تفصيلي للبنية (ARCHITECTURE.md)
```

اقرأ `docs/ARCHITECTURE.md` لفهم كيف يعمل اللعب أونلاين والبلوتوث بنفس
البروتوكول، و`mobile/README.md` لخطوات تشغيل التطبيق فعليًا على جهاز.

## البدء السريع

### الخادم

```bash
cd server
npm install
npm test      # 13 اختبارًا وحدويًا لمنطق الغرف والتحقق من الإصابات
npm start     # يستمع على ws://localhost:8080
```

### تطبيق الهاتف (Flutter)

```bash
cd mobile
flutter pub get
flutter run
```

مجلدا `android/` و`ios/` جاهزان بالفعل مع أذونات البلوتوث/الموقع المطلوبة.
راجع `mobile/README.md` لكيفية الاتصال بالخادم من محاكٍ أو جهاز حقيقي.

## حالة المشروع بصراحة

هذه **نسخة أولى (MVP)** — وتم تشغيل مباراة أونلاين حقيقية كاملة بين "جهازين"
فعليًا (متصفحين منفصلين يتحدثان مع الخادم الحقيقي عبر WebSocket، بدون أي
محاكاة) للتحقق منها، وليست تطبيقًا جاهزًا للنشر على المتاجر مباشرة:

- ✅ **الخادم**: منطق الغرف، توازن الفرق، الجاهزية، بدء اللعبة، التحقق من
  الإصابات — **13 اختبار Jest ناجح** + اختبار end-to-end عبر WebSocket حقيقي.
- ✅ **تطبيق الهاتف**: تم تثبيت Flutter SDK فعليًا والتحقق من المشروع بالكامل
  — `flutter analyze`: لا توجد أي مشاكل، `flutter test`: 6/6 ناجحة. مجلدا
  `android/` و`ios/` مُولَّدان ومُدرجان في المستودع مع كل الأذونات اللازمة.
- ✅ **مُختبر فعليًا بمباراة حقيقية كاملة (وليس فقط تحليلًا ساكنًا)**: بُني
  التطبيق لهدف الويب (`flutter build web`) فقط كوسيلة لتشغيله فعليًا في هذه
  البيئة (متصفح Chromium)، وشُغِّلت مباراة أونلاين حقيقية بين متصفحين
  منفصلين يتحدثان مع نفس خادم Node.js الحقيقي: إنشاء غرفة → انضمام بالكود →
  توازن الفريقين (أحمر/أزرق) → الجاهزية → بدء اللعبة → تحريك اللاعب عبر عصا
  التحكم → إطلاق نار → تحقق الخادم من الإصابة → **انخفاض شريط الصحة فعليًا
  على شاشة اللاعب المُصاب**. هذا الاختبار الحي كشف وأصلح خطأين حقيقيين لم
  يكن التحليل الساكن ليكشفهما:
  1. **قطع الاتصال عند بدء اللعبة**: كانت `LobbyScreen.dispose()` تُغلق
     اتصال الشبكة المشترك بمجرد الانتقال لشاشة اللعبة (لأن Navigator يتخلص
     من الشاشة القديمة)، فيموت الاتصال بعد بدء المباراة بأجزاء من الثانية.
     تم إصلاحه بتتبع ما إذا كان الاتصال قد سُلِّم فعليًا لشاشة اللعبة قبل
     إغلاقه.
  2. **تراكب اللاعبين عند البداية**: كل اللاعبين كانوا يبدأون بالضبط عند
     نفس النقطة (0,0) فوق بعضهم تمامًا. تم إصلاحه بتوزيع نقاط بداية مختلفة
     حسب الفريق (يسار الساحة للأحمر، يمينها للأزرق).
  (الويب ليس هدف النشر النهائي — فقط أداة تحقق؛ مجلد `mobile/web/` تُرك في
  المستودع لأنه يعمل فعلاً ويمكن إعادة استخدامه لتجربة سريعة في المتصفح.)
- ✅ **CI**: `.github/workflows/ci.yml` يشغّل اختبارات الخادم والتطبيق تلقائيًا
  على كل push.
- ⚠️ **لم يُختبر بعد**: البناء الفعلي لملف APK/IPA (يحتاج Android SDK / Xcode
  غير متوفرين في بيئة الإنشاء)، واللعب الفعلي عبر بلوتوث بين جهازين حقيقيين
  (المحاكيات عادة لا تدعمه، والويب لا يدعم `nearby_connections` أصلاً).
- ❌ **غير موجود بعد**: حسابات مستخدمين، حماية من الغش متقدمة، تحسين حركة
  الشبكة (interpolation/throttling)، دعم أكثر من فريقين، أصوات ورسومات
  احترافية، كاميرا تتبع اللاعب (حاليًا لا كاميرا، فاللاعب البعيد عن الزاوية
  يخرج عن حدود الشاشة)، إعداد النشر الفعلي على Google Play / App Store
  (يتطلب حسابات مطوّر، توقيع التطبيق، ومراجعة كل متجر).

## خارطة طريق مقترحة

1. إضافة كاميرا تتبع اللاعب المحلي (أهم فجوة بصرية ظهرت أثناء الاختبار الحي).
2. اختبار اللعب بين هاتفين حقيقيين (أونلاين ثم بلوتوث تحديدًا).
3. نشر الخادم على استضافة دائمة (Render / Fly.io / VPS) بدل `localhost`،
   وتحديث `kDefaultServerUrl` في `mobile/lib/screens/lobby_screen.dart`.
4. تحسين تجربة الشبكة: تقليل تردد `player_state`، إضافة تنعيم للحركة.
5. إعداد أيقونة/اسم التطبيق، توقيعه (keystore لأندرويد، شهادة لـ iOS)،
   وإرساله لمراجعة المتاجر.
